    Agent OS threat model

    Status: Phase 5 complete, reviewed 2026-11-09. Revise this file for every change that touches privilege escalation, credentials, filesystem mounts, networking, or GUI capture.

    Check names in this document are rows in tests/isolation/checks.tsv. The isolation design explains the controls.

    Protected assets#

    IDAssetWhy it matters
    A1Project workspace, home, cache, state, and artifactsSource code and agent memory belong to one project.
    A2Project credentials: Git, registry, and API tokensA leak acts with the project's external authority.
    A3GUI sockets, recordings, screenshots, and input tracesCaptures can contain secrets typed on screen.
    A4Host configuration, boot files, and system servicesA change here persists beyond any project.
    A5APT and dpkg state, and global toolchainsEvery project executes this software.
    A6Administrator and system-agent credentials, and SSH host keysThese grant host control or impersonation.
    A7/var/lib/agent-os/metadata and managed snapshotsTampering rewrites identity mappings or recovery data.
    A8Audit historyWithout it, nobody can reconstruct a privileged change.
    A9Host availability, including the SSH management reserveA runaway project can lock out the administrator.

    Attacker capabilities#

    IDAttackerAssumed capability
    T1Compromised or misaligned project agentRuns arbitrary code as its project UID, for as long as it wants.
    T2Malicious project dependency, for example an npm post-install scriptThe same capability as T1.
    T3Compromised system agentSends any request that its identity is allowed to send to hostd. It has no root shell.
    T4Malicious Debian or toolchain package approved by policyRuns as root during installation.
    T5Network attackerReaches any port that the host exposes.
    T6Holder of a kernel exploitCrosses every boundary in this document.

    A prompt-injected agent is T1 or T3. The design does not try to detect injection. It limits what the affected identity can do.

    Trust boundaries#

    IDBoundaryEnforced byStatus
    B1Project to projectSeparate UIDs, mode 0700 directories, mount, IPC, and network namespaces, ProtectProc=invisibleTested
    B2Project to hostNo capabilities, no new privileges, read-only system paths, private /run, network namespace, and nftables input policyTested
    B3Project to system agentSeparate UID, private /run, socket group, and hostd accepts peers by SO_PEERCREDTested
    B4System agent to rootTyped hostd operations, policy, human approval, and auditTested. Package scripts remain gap 6.
    B5Network to hostOpenSSH keys only, and no remote root. The VM image enforces this. Private networking is still design onlyTested for the VM image
    B6Project to kernelSeccomp filter and hidden kernel interfaces reduce exposure onlyPartial by design

    Accepted gaps#

    Each gap stays open until a later change closes it. The suite marks the first one as gap, so it fails when the behavior changes.

    1. /etc/passwd reveals project names. passwd_project_names proves the access. Project names must not contain secrets.
    2. Network egress is unrestricted. T1 can send any readable project data to the internet. NAT also lets it reach the LAN and cloud metadata addresses. Per-project egress policy is future work.
    3. User namespaces stay enabled. user_namespace requires them, because Chromium and Electron sandboxes need them in Phase 4. They add kernel attack surface for T6.
    4. The kernel is shared. T6 defeats the design. Use the vm execution profile for workloads that warrant a separate kernel.
    5. Same-project processes are not isolated from each other. An agent can read every credential that its project holds. A secret delivered to a project is visible to all of that project's code.
    6. Package installation scripts run as root. T4 has full control during installation. Policy and approval reduce the chance of T4, and they do not contain it. A script can also add file capabilities, which the content scan cannot see.
    7. Projects can still fill the shared Btrfs filesystem together. The default limit is 80% for each project, so several projects can exceed the disk. A project can also write outside its limit in the time before the storage check enrolls a new subvolume, at most one minute. Under critical pressure the check stops the largest project, which can be the wrong one. Snapshots are not counted against a project's limit.
    8. A project can create its own Btrfs subvolumes. systemd cannot filter ioctl arguments, so the sandbox cannot stop this. Snapshots omit their contents, and the snapshot reports how many it omitted. A project that creates shared subvolumes also forces quota rescans, and limits are not exact during a rescan.
    9. Project output can contain terminal escape sequences. run, shell, and logs pass the output to the administrator's terminal unfiltered.
    10. Project output goes to the host journal. journald's size limits apply, and the journal keeps secrets that a project prints. A project can also push out older host log entries.
    11. The system agent can grow the audit log. T3 can send refused requests until the data disk fills. Log rotation does not exist yet. Projects cannot reach this path.
    12. A busy lock can delay the administrator. T3 can keep requesting long plans, so an administrator's change can be refused as busy. Stopping agentos-hostd.socket ends this.
    13. A human approves what change show displays. The plan lists actions, units, and setuid files. It cannot judge whether a package is trustworthy.
    14. Backups are not encrypted or signed. A stream holds every project secret. The checksum catches damage, and someone who can rewrite the backup can also rewrite the checksum. The checks at recover limit what a forged backup can do, but the forged project data is still restored. Encrypt and authenticate the stream outside agentos.
    15. agentos does not schedule or rotate backups. The operator pulls them. A backup is always a full stream.
    16. A GUI capture holds whatever was on screen. Screenshots and recordings stay in the project and enter its snapshots and backups. agentos-gui rm removes them from the live tree only, and nothing expires them automatically.
    17. Graphical sessions do not contain the applications in them. Applications in one session can capture each other and inject input through the compositor. A process that leaves its process group stays alive after stop, until its project command ends.
    18. A viewer can send input. An administrator who opens view can click and type in the session, like the project itself can.
    19. A leaked connection keeps its identity. SO_PEERCRED describes who connected. If the system agent passes an open socket to another process, that process acts as the system agent.
    1. The first boot trusts whoever supplies the boot credential. Until an administrator key exists, anyone who controls the hypervisor can enroll one. That party can already read the disk, and the file is never overwritten once it exists. An installed host already has a key, so this applies to the VM image.
    2. The admin account has passwordless sudo. A stolen administrator key is root on the host. The account has no password to type, and the image relies on the key alone.
    3. The installer ISO is not signed. Its checksum catches damage, and someone who can replace the ISO can replace the checksum too. Secure Boot must be off to start it. The installer also runs as root on the console, so anyone at the console before the disk is chosen can install their own key.

    Rules for later phases#

    • hostd listens only on a Unix socket. File ownership and SO_PEERCRED cannot check a network peer.
    • Root-run tooling must not open a project path through a systemd StandardOutput=file: setting. PID 1 would follow a symlink that the project planted.
    • Host services must not trust a connection because it came from 127.0.0.1.
    • Root-run tooling must not follow symlinks inside a project directory.
    • Bind any GUI viewer to a project-private socket, never to a host port by default.
